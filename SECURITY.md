Security and Sensitive Data Guidance

Summary
- `firebase_options.dart` contains Firebase configuration values (API key, project id, etc.). While those values appear public in mobile apps by design, treat any long-lived service credentials as sensitive and restrict their use.

Recommendations
1. Restrict API keys and services in Google Cloud / Firebase console
   - Restrict API key usage to specific platforms (Android package name, iOS bundle id) and set HTTP referrer restrictions where applicable.
   - Use Firebase Security Rules to control read/write access to Firestore instead of relying on client-side checks.

2. Avoid embedding server-side secrets in the client
   - Move any secret credentials to a server-side component (Cloud Functions, custom backend) and expose minimal functionality via authenticated APIs.

3. Rotate keys and monitor usage
   - Regularly rotate API keys and enable billing alerts and usage monitoring in the Firebase/GCP console.

4. Source control hygiene
   - Do not commit other secret files (service account JSON) to VCS. Add them to `.gitignore` and share via secure channels.

5. Review Firebase Rules and IAM
   - Ensure Firestore rules allow only authenticated users to read/write needed collections and that rules enforce expected field shapes and indexes.

6. Local dev and CI
   - Use environment-specific configuration (dev/staging/prod) and ensure CI does not leak secrets in logs.

Notes
- `firebase_options.dart` generated by the FlutterFire CLI is expected to be in the repo for client apps. These values are not considered high-entropy secrets like service account keys, but platform restrictions and security rules are essential to prevent abuse.
